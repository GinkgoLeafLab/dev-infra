# PR 写锁：评审在飞时，让「结论当场作废」可见

- **日期**：2026-09
- **状态**：草案
- **触发**：`GTO-Trainer#182`（一份**纯文档、零代码**的方案文档）走了 9 轮评审。
  其中**两轮已经判「通过」，都因为作者随后推了新 commit 而作废**。第一次作废作者知道；
  更早一次落在旧 SHA 上，作者**事后自己算出来的**。这份方案修的是那个窗口。

## 要解决什么问题

**谁也不知道「有人正在审这个 SHA」。**

现有两条机制都只回答「这个 SHA **通过**了吗」，而且都在评审**结束之后**才写：

| 现有机制 | 回答的问题 | 何时写 |
|---|---|---|
| `review` / `qa` 这两个 commit status（`review-gate.yml` / `qa-gate.yml`） | 「这个 SHA **通过**了吗」 | 评审**结束**后 |
| **缺的** | 「有人**正在审**吗」 | — |

于是「评审进行中」这一段时间里，**任何提交都能自由推进，而没有任何人因此报错**：

```
作者推 commit  →  评审开始审这个 SHA
                      ↓（评审要跑十几分钟）
                 作者看到已发出的必修 → 立刻改 → 立刻推
                      ↓
                 评审的目标 SHA 已经过期 → 这一轮的结论作废 → 只能再派一轮
```

**失败是静默的**，这正是它反复发生的原因。代价实打实：9 轮评审、60+ 条 webhook 噪音，
两轮已判「通过」的结论作废。

## 调研

> 本节的每一条都真的调过 API / 读过文档原文。**拿不到的写「拿不到」**，不用「据了解」搪塞。

### 事实一：ruleset 只覆盖默认分支，而 PR 的提交推在特性分支上

实调 `GET /repos/GinkgoLeafLab/GTO-Trainer/rulesets/21374227`（2026-09-20）：

```json
{"name": "main protect", "enforcement": "active",
 "conditions": {"ref_name": {"include": ["~DEFAULT_BRANCH"]}},
 "rules": [{"type": "deletion"}, {"type": "non_fast_forward"},
           {"type": "pull_request", ...},
           {"type": "required_status_checks",
            "parameters": {"required_status_checks": [
              {"context": "test"}, {"context": "review"}, {"context": "qa"}]}}],
 "current_user_can_bypass": "never"}
```

**只护 `~DEFAULT_BRANCH`**——PR 的提交推在**特性分支**上，那里没有任何 ruleset。

### 事实二：必需检查的语义是「不能合并」，**不是「不能 push」**

GitHub 官方文档 *Available rules for rulesets* 的
[Require status checks to pass before merging](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging)
一节原话：

> After enabling required status checks, all required status checks must pass before
> collaborators can **merge** changes into the branch or tag.

**是 merge，不是 push。** 这一条把「拒绝 push」这个措辞直接否掉了。

### 事实三：能拦 push 的规则存在，但拦不了「这个 PR 有没有人在审」

同一页记录了 push rulesets（`Restrict updates` / `Restrict creations` / `Restrict deletions`）
与 `Block force pushes`。**但它们是按「谁 / 什么路径 / 多大」限制的静态规则**，
**没有一条能表达「有锁时不许推」这种条件判断**——那需要读一个会变的状态。
（`Restrict updates` 是「只有有 bypass 权限的人能推」，把作者整个挡在门外，不是我们要的。）

### 事实四：CI 拦不住 push，但能当场把它写成失败检查

`on: push` 的 workflow 在**推完之后**才跑，所以它**永远无法阻止那次 push**。
它能做的是**在同一秒把「你的结论已作废」写成一条失败的 commit status**，PR 当场变红。

### 三个必答问题

1. **有没有现成的标准？** 有——**commit status + 必需检查**，本仓已经在用
   （`review-gate.yml` / `qa-gate.yml`）。本方案就是复用它，不新发明机制。
2. **别人踩过什么坑？** 「必需检查被 workflow 级 `paths` 过滤跳过 → 永远停在
   "Expected — waiting for status" → PR 永远合不了」——这条本仓
   `test.yml` 与 `qa-gate.yml` 的注释里已经记着并各自下了禁令。
   本方案**不加 `paths`**，理由同那两条。
3. **有没有更省的路？** **有，而且它就是选定方案**（见下）。
   原设计是「新建一个 `review/in-flight` 锁 + 新建一条 gate」；调研之后发现
   `review-gate` **本来就已经挂在 PR 上、本来就认得 head SHA**，
   加一个 `synchronize` 就能让它自己报「结论作废」——**不需要新 gate、不需要第二条必需检查**。

## 备选方案

| 方案 | 怎么做 | 代价 | 否掉的理由 |
|---|---|---|---|
| **① 什么都不做** | 维持现状 | 0 | 已经咬人 9 轮，且**失败静默**，会继续复发 |
| **② 本地 `pre-push` hook** | 各仓 `.githooks/pre-push` 读锁 | 低 | **只拦有 hook 的机器**。Claude Code / 别的 agent / 网页提交都没有它 —— 挡不住这次事故里的真实对手。**只可作为补充** |
| **③ 分支保护加到每个特性分支** | 给每个 PR 分支加 ruleset | 高 | 每个 PR 分支一份、要随开随建随删，运维重量与收益完全不成比例 |
| **④ 新建独立 gate + 新标签 `review/in-flight`** | 全新一条必需检查 | 中 | **新建第二条必需检查**会引入它自己的一类失效（缺席即拦 → 忘报告就永远合不了），而收益和 ⑤ 一样 |
| **⑤ 让 `review-gate` 自己报「结论作废」** ✅ | 给 `review-gate` 加 `synchronize`，读锁 + 比对 SHA，作废时写 failures | 低 | **选定** |

**⑤ 为什么比 ④ 省**：`review-gate` 已经是必需检查、已经挂在 head SHA、已经认得 PR 事件。
「结论作废」天然就是 **`review` 这个检查自己的结论**——不需要新的检查名、
不需要新的缺席即拦的风险面。

## 选定方案

### 不变式

> **对某个 PR 的评审一旦开始，它审的就是那一刻的 `head_sha`。
> 在那个结论回来之前，那个 PR 的 head 不得前进。**

这是**按 PR 范围的写锁**，不是「有 agent 在忙就全停」——并行的另一个 PR 不受影响。

### 锁为什么必须建在 GitHub 上（最重要的一条）

评审者可能是 DSH 派出的 subagent、**Claude Code 在另一台机器上**、或者**人手动起的会话**。
前一种 DSH 插件看得见（`agent/created` / `agent/status`），**后两种看不见**。

**三方唯一共享的面是 GitHub 本身。** 所以锁必须是 GitHub 上的**可读状态**，
由**动作方写**、由**gate 读**。锁不能建在任何 agent 框架里。

### 形状

复用本仓已有的房规「状态写在标签上、由动作方写、由 workflow 读」（同 `status/*` 一族）。

| 动作 | 怎么做 |
|---|---|
| **取锁** | 评审者打 `review/in-flight` 标签 + 一条固定标题的评论写明 `base_sha` / `holder` / 到期时间 |
| **验锁** | `synchronize` 时读锁，比对 `base_sha` 与旧 head |
| **放锁** | 评审者自己摘标签；**TTL 到期由 gate 自动释放并留痕** |
| **告警** | 发现结论作废 → 在**新 head SHA** 上写一条 `failure` 的 `review` 检查，描述写明「评审结论已作废（base=…）」 |

### 明确不做什么

- **不做「拒绝 push」。** GitHub 拦不住（事实一 / 二 / 三），硬做只能靠给每个特性分支加
  ruleset（方案 ③，代价不成比例）。**这把锁不阻止提交，它让「新提交使结论作废」当场上报**
  ——这正是这次事故里最缺的东西：把「你的结论已经作废了」从**作者事后自己算**
  变成**系统当场说**。
- **不新建第二条必需检查**（方案 ④）。
- **不改 `pull_request_target` 的安全地基。**

### 已知边界（写下来，而不是让它静默）

1. **一个 PR 仍可新增 `on: pull_request` 的同名 workflow 自写 `review` 检查**——
   必需检查是按名字匹配的。`review-gate.yml` 的注释已经记着这条，**本方案不改变它**，
   那条路只能靠评审拦。
2. **锁依赖评审者自觉取锁。** 忘记取锁 = 没有锁 = 回到今天的行为（**不会更糟**）。
   这是刻意的失败方向。
3. **TTL 到期自动释放会留痕**（写注释说明「锁是超时释放的，不是评审者放的」），
   否则「锁自己消失了」会变成新的静默失败。

## 代价

- **一次性**：一个组合动作 + 它的测试 + `labels.json` 加一个标签 + `review-gate` 加一个事件类型。
- **持续**：每次 `synchronize` 多一次 API 读锁，跑在既有 runner 上，**新增配额可忽略**。
- **它挂了会怎样**：读锁失败 → **不再报「作废」**，退回今天的行为（静默过期）。
  **失败方向是「少一层保护」，不是「误拦 PR」**——这是选定的方向：
  宁可少报，也不能因为锁挂了就让所有 PR 合不了。
- **隐私与合规**：无新增外部依赖，全部走 GitHub 自己的 API。

### 实现时自己踩到、并已经钉住的两个坑

两条都**只在真跑起来才暴露，而且都是静默的**，所以各写了一条断言（W11 / W12）：

1. **`gh api --paginate` 配 `--jq` 吐出来的不是一段合法 JSON**。gh 是把每一页的 jq
   结果**各自序列化后首尾相接**，页数 > 1 时 `JSON.parse` 直接抛（实测：
   `[{"body":"a"}]\n[{"body":"b"}]`）。要配 `-q` 再用 `jq -s 'add // []'` 收成一段。
2. **`$GITHUB_OUTPUT` 是「一行一条」的格式**，值里带换行会被 GitHub 拒掉这一步
   （"Invalid format"）。而**评论体里一定有换行**——那正是它的用处。
   必须用 heredoc 定界符写。
