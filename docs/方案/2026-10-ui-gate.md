# UI 评审放行门（ui-gate）

- **日期**：2026-10
- **状态**：实现与它在同一个 PR 里。**照实写：这份是实现做完之后才落笔的，不是动手之前写的**——
  结构（参数化、默认 qa）在动手前已定，调研（官方文档那两条）是写文档时才补读的原文
- **触发**：产品仓 `GTO-Trainer` 要新增 UI 设计师 / UI reviewer 两个 agent 角色（上游 `dev-agents#6`），
  Dean 拍板 **UI 评审要做成合并前的必需检查**，形状和 `qa` 一样。第一个消费方是 `GTO-Trainer`。

## 要解决什么问题

UI 评审的结论今天没有任何东西能强制：评审 agent 说「这版界面可以」，PR 照样能在没人评审过 UI 的情况下合进去。
`review`（代码评审）和 `qa`（功能测试）都是「标签 → commit status → 必需检查」这个形状，
UI 评审需要同一种保证：**标了要 UI 评审的 PR，合进去的必须是过了评审的那一版**；没标的 PR 不被拦。

## 调研

每条都是读过原文的；没拿到的写了「拿不到」。

1. **必需检查被跳过会停在 Pending**。GitHub 官方「Troubleshooting required status checks」：
   workflow 被 path / branch 过滤或提交信息跳过时，"Associated checks stay in a 'Pending' state and block merging."，
   建议 "Avoid requiring workflows that can be skipped."（
   <https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks>）。
   ——所以 `ui` 和 `qa` 一样必须**每一版都报告一次**，「不需要」表达成 `success` 而不是「不报告」。
   同一页还写了 "If a check and a commit status have the same name, both must pass when that name is required."：
   检查名 `ui` 不能和别的检查撞名。
2. **可复用工作流的权限只能降不能升**（<https://docs.github.com/en/actions/sharing-automations/reusing-workflows>
   原话 "permissions can only be maintained or reduced—not elevated—throughout the chain."），
   以及 `workflow_call` 可以声明并传入 inputs。这决定了 ui-gate 的 caller 与 qa-gate 的 caller 同形：
   `on` / job 级 `if` / `permissions` 留在 caller。
3. **同类做法**：本仓 `qa-gate`（`.github/actions/qa-gate/`）就是这个形状，且已在 `GTO-Trainer` / `GTO-Trainer-studio`
   上实跑；放行检查必须是 commit status 而不是 check run，是在 `GTO-Trainer` 上实测的结论（原因没查到出处，
   见 `qa-gate.js` 里的注释），ui 门继承，不重做。
4. **社区现成 action**：想过「用别人的 label-gate 类 action 代替自写」，**没有逐个评估**——
   `qa-gate` 的判定里最值钱的是「防过期标签快照」那段（`ui-passed` 只认「这个事件本身就是在打它」），
   这是 `qa-gate.js` 注释里记着的一次真实竞态推演的产物；换一个我们读不全源码的第三方 action，
   等于把必需检查的判定交给一段没有我们的测试钉着的代码。所以不用。查过的结论是「不合适」，不是「没查」：
   不合适的理由是上面这一条，而不是功能缺失。

## 备选

| 方案 | 做法 | 否决 / 采用的理由 |
|---|---|---|
| A 什么都不做 | 让产品仓 UI 评审只靠 agent 自觉 | 否决。**这正是「没有强制」本身**：Dean 已明确要必需检查 |
| B 复制一份 qa-gate | `ui-gate.js` + `ui-gate/action.yml` + `ui-gate.test.js` 整份抄 | 否决。判定里有一段防竞态的逻辑，抄两份就会各自漂：以后任何一边修了过期快照的洞，另一边不知道。这个脚本的失效方向是「静默放行」，不该有两份 |
| C 把 qa 门参数化，ui 是第二个取值 | 一份脚本 / 一份动作；`GATES` 表放差异（门名、两个标签、四句描述）；动作加 `gate` 输入，默认 `qa` | **采用**。见下 |
| D 通用 `label-gate` 重写，qa / ui 都改成薄壳 | 抽象更干净 | 否决。要改 qa 那条已在三个仓上跑的路径的文件名与接口，风险与收益不成比例 |

## 采用 C 的做法，以及它对 qa 那条路的风险

- `qa-gate.js`：新增 `GATES = { qa, ui }`；`decide()` / `statusBody()` 多一个**末位带默认值**的参数 `gate`（默认 qa）；
  CLI 读 `QA_GATE_NAME`，**空串 / 未设当 qa**，认不得的名字**抛**（job 红 → 检查缺席 → 拦住；
  不能悄悄退回 qa，否则一条 ui 的接线错误会在 `qa` 上写结论）。
  环境变量名仍叫 `QA_GATE_*`，为的是 qa 这条路的每个字节都不动。
- `action.yml`：多一个 `gate` 输入，**默认 `qa`**，只被放进 `QA_GATE_NAME`。`qa-gate.yml` 不传它。
- 新的可复用工作流 `ui-gate.yml`：同 qa-gate.yml 的步骤，`uses: $/.github/actions/qa-gate` 后面跟 `with: gate: ui`。
- **qa 一路的风险与保证**：
  - 现有 `qa-gate.test.js` 一个字不改全绿（改造前后 112 条）；`qa` 的四句描述在 `GATES.qa` 里与改造前**逐字相同**，
    该测试钉着 `context === "qa"`、描述含「不是这个事件打上的」。
  - 消费仓钉的是 dev-infra 的不可变 tag，**改这个仓的文件对已发布的 tag 零影响**；
    只有它们升 `uses:` 到新 tag 时才拿到新脚本，那时拿到的 qa 行为与现在逐字相同（上一条）。
  - 剩下的真实风险只有一条：**共享脚本以后被改坏，会同时坏 qa 和 ui**。
    这是共用一份的固有代价（B 方案是用「两份各自会漂」换掉它）；缓解是两门共用同一套断言——
    `ui-gate.test.js` 对两道门各跑一遍最要命的判定，所以一边的回归会同时红。
- **门名接错是 C 特有的新失效**：`ui-gate.yml` 若漏了 `gate: ui`，消费仓会在 head SHA 上写出 `qa`、缺 `ui`，
  `ui` 永远停在 `Expected`。`ui-gate.test.js` 的 U3 把这两行钉住；`adopt` 的 `lintCaller('ui-gate')`
  还会判 caller 的 `uses:` 指的是 `ui-gate.yml` 而不是 `qa-gate.yml`。

## 标签清单

`labels.ui.json` 单独一份（`ui-required` / `ui-passed`），和 `labels.qa.json` 同理：只有真的装了 ui-gate 的仓才该有，
否则等于给没人读的标签一份正式定义。`labels-sync` 的组合动作与可复用工作流加可选输入 `ui-labels`（默认 false）。
基础清单里不许出现 `ui-*`（`labels.test.js` 钉着），ui 清单的名字与 `GATES.ui` 对账。

## 不做什么

- **不动 `review` / `qa` 的任何行为**，不碰 review-gate-lock。
- **不改本仓自己的 `self-*.yml`**：本仓没有 UI，不装 ui 门（和不装 qa 门同理）。
- **不在这个 PR 里打 tag、不改任何消费仓。** 消费仓要等新 tag 发出来后再加 caller。
- 不替消费仓决定 `ui-required` 的判据（哪些改动算 UI）——那是产品仓 CLAUDE.md 的事。

## 消费方要做的三件事（落地后搬进 README，这里只记方案时的清单）

1. 放一个 `ui-gate.yml` caller（`adopt --ui` 能生成），钉新 tag；`labels-sync` 的 caller 加 `ui-labels: true` 并升到同一个 tag。
2. 人去 ruleset 里把 **`ui`** 加成必需检查（agent 改不了仓库设置）。
3. UI reviewer 判通过时打 `ui-passed`；开 PR 的会话判要不要 UI 评审并打 `ui-required`。
