# 标签竞态：并发组只按 PR 号分，重评被「注定 skip」的 run 挤掉

- **日期**：2026-11-01
- **状态**：已修复（同一 PR 内改了 qa / ui / review 三份 caller 模板与本仓的 self-review-gate，
  并让 qa / ui 的判定改读实时标签）
- **触发**：核查 `GinkgoLeafLab/Tianshu#199` 时发现的真实缺陷：一个纯 UI 改动
  （94 个文件里 88 张设计稿截图 + `src/board/*`）从未经过 UI 评审，head `89d6917`
  上却有 `ui` = success，足以满足合并规则。

## 现象

PR #199 打开时 `tianshuplugin[bot]` 在 300ms 内先后打上 `ui-required`、
`qa-required`。head `89d6917` 上的 commit status 实测：

| 时间（UTC） | context | state | 描述 | 写入的 run |
|---|---|---|---|---|
| 07:36:43 | `ui` | success | 未标记需要 UI 评审（没有 `ui-required`） | 41285479459（opened） |
| 07:36:43 | `qa` | success | 没有 `qa-required`，跳过 QA | 41285479403（opened） |
| 07:36:51 | `qa` | failure | 标了 `qa-required`，但这一版还没通过 QA | 41285482991（qa-required labeled） |
| 07:39:23 | `ui` | failure | 标了 `ui-required`，但这一版还没通过 UI 评审 | 41285642589（人工把 `ui-required` 摘了又打） |

`ui` 从 07:36:43 到 07:39:23 之间一直是 success。那三分钟里，PR 已经带着
`ui-required`，却没有任何人重评 UI。

## 根因：不是「快照过期」，是「重评那次根本没跑」

`ui-gate` / `qa-gate` 的 caller 里，并发组只按 PR 号分：

```yaml
concurrency:
  group: ui-gate-${{ github.event.pull_request.number }}
  cancel-in-progress: false
```

而 job 级的 `if` 要等**轮到这次 run 执行**才判。「同一组里新排队的 run 会取消
先前排队的 run」——`cancel-in-progress: false` 只保证在跑的那次不被砍，**排队的那次
照样被挤掉**。于是：

1. `opened` 起一次 run（run 41285479459），快照里没有 `ui-required`，写 `ui` = success；
2. 300ms 后 `ui-required` 打上，起 run 41285482941，排在 opened 后面；
3. 291ms 后 `qa-required` 打上，起 run 41285483063，**同组**，把仍在排队的
   41285482941 挤掉，自己成为唯一排队的 run；
4. opened 跑完，41285483063 开始执行，job 级 `if` 只认 `ui-*`，于是 **skipped**；
5. `ui` 停在 opened 那次写的 success 上，再没有 run 去覆盖。

run 名单就是证据：

| 工作流 | run | 事件 | 结论 |
|---|---|---|---|
| ui-gate | 41285479459 | opened | success（写了 `ui` = success） |
| ui-gate | 41285482941 | `ui-required` labeled | **cancelled**（排队时被挤掉，jobs 为空） |
| ui-gate | 41285483063 | `qa-required` labeled | skipped（`if` 不认这个标签） |
| qa-gate | 41285479403 | opened | success |
| qa-gate | 41285482891 | `ui-required` labeled | **cancelled** |
| qa-gate | 41285482991 | `qa-required` labeled | success（写了 `qa` = failure） |

qa 当时是对的，**但那只是顺序的运气**：两个 labeled run 同组，后到的那个活下来。
把两个标签的先后对调，qa 同样会被打绿、ui 反而正确。所以这不是「ui 门的问题」，
是 caller 并发组的结构性问题，qa / ui 同形，review-gate 也是同一个形状
（它失败方向是安全的：`review` 缺席即拦，但「评审通过后 PR 莫名卡着」同样是故障）。

第二层问题：即使重评的 run 跑起来，它读的 `github.event.pull_request.labels`
也是**事件创建那一刻**的快照。webhook 送达顺序不保证，一个先发生、后送达的
`opened` 会带着旧快照最后执行，把后来的 failure 覆盖成 success。只修并发组挡不住这条。

## 修法

### 1. 并发组按「这次事件会不会真的跑判定」分成两组

```yaml
concurrency:
  group: ui-gate-${{ github.event.pull_request.number }}-${{
    (github.event.action == 'labeled' || github.event.action == 'unlabeled')
    && !startsWith(github.event.label.name, 'ui-') && 'skipped' || 'live' }}
  cancel-in-progress: false
```

注定 skip 的 run 只能取消同类，碰不到真正要重评的那次。分组谓词必须与 job 级
`if` 同义——只改一处等于把洞换个形状打开；`adopt` 的体检与
`.github/actions/qa-gate/gate-race.test.js` 都钉着这条。
review-gate 用同一个形状：`synchronize` 或 `review-passed` 进 `live`，其余进
`skipped`。

### 2. qa / ui 的判定改读执行这一刻的标签

可复用工作流在判定前加一步 `live_labels`：`gh api repos/$REPO/pulls/$PR` 取
`.labels[].name`（经 jq 拼成 JSON 数组），经组合动作的 `labels` 输入交给判定脚本；
读不到就让这一步红，并由下一步在这个 head SHA 上显式写 `error`（语义是「判不了」）——
新 SHA 上写的就是这条 error，同一 SHA 上则盖掉早先的 success，两种都是拦住而不是放行。
事件类型与「这次打的是哪个标签」仍按事件传进去——
`qa-passed` / `ui-passed` 只认「本次事件就是在打它」这条判断不变，两件事互不替代。

两条都必要：只做 1，乱序送达仍可能让旧快照最后落笔；只做 2，被挤掉的那次
根本没机会现读。

## 改了哪些文件

- `adopt/templates/qa-gate.yml`、`ui-gate.yml`、`review-gate.yml`：并发组分区；
- `.github/workflows/qa-gate.yml`、`ui-gate.yml`：新增 `live_labels` 步骤与现读失败时的
  `error` 兜底，把实时标签传给组合动作；
- `.github/actions/qa-gate/action.yml`：新增 `labels` 输入，优先于事件快照；
- `.github/workflows/self-review-gate.yml`：本仓自己的 review caller 同一处修复；
- `adopt/adopt.js`：`lintCaller` 增加「并发组必须按判定谓词分区」的硬检查；
- `.github/actions/qa-gate/gate-race.test.js`（新增，进 `.github/workflows/test.yml`）：
  按 GitHub 并发语义模拟 PR #199 的事件序列，旧分组必须复现 success，新分组必须是
  failure；并钉住实时标签那条接线。

## 不做什么

- 不动 PR #199 的代码；#199 的 UI 真评由 UI 评审人另做。
- 不把「并发组分区」搬进可复用工作流：并发只能由 caller 定义，而被调用方读不到
  caller 的 `concurrency`。各消费仓要等升到带这处修复的新 tag 后才生效。
- 不修 `qa-passed` / `ui-passed` 的过期快照判断：那是另一类失效（摘标签的 DELETE
  未落地时现读仍是旧值），已有「只认本次事件打上的 passed」在挡，本次不改它的语义。
